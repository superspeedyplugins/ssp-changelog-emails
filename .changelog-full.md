# ssp-changelog-emails — full changelog

The engineering account behind each `readme.txt` entry. Started at 1.6.2; earlier
releases are documented only by their readme entries, which for this plugin are
already unusually detailed.

## 1.6.7 (18th September 2026)

### Calculated licence audience labels

> * Changelog Support Email previews now divide owners into LICENSED, EXPIRED, WINBACK and UNKNOWN using their current licence and renewal dates.

The selected `audience_scope` already decided whether each owner should receive a changelog
email, but the preview reduced every rejected owner to the generic Filtered count. The callback
now returns the unchanged send decision plus a transient audience label when Super Speedy Emails
1.23.1 or later is active.

LICENSED uses the existing active-licence test. A non-current licence whose most recent known
renewal date passed less than six calendar months ago is EXPIRED. One at least six months old is
WINBACK. A non-current ownership with no usable renewal date is UNKNOWN rather than being assigned
a false expiry age. The detailed 6-to-12 and over-12 filters remain available, and both are shown
as WINBACK in the top-level breakdown.

The add-on keeps returning its original boolean on an older Emails core. This preserves the
selected audience when the add-on is deployed before the core that understands structured
results. The existing boundary and duplicate-ownership test now also covers all four labels.

Execution plan and verification: `.docs/archive/2026-09-18-licence-audience-breakdown.md`.

## 1.6.2 (18th August 2026)

### Expired-licence audience bands

> * Three new "Send to" audiences on each changelog Support Email: licences expired
>   within the last 6 months, expired 6 to 12 months ago, and expired more than
>   12 months ago. The bands never overlap, so separate records can cover the whole
>   expired base without anyone receiving two emails.
> * A licence with no stored renewal date is treated as expiring 365 days after its
>   last purchase, matching how active licences are already judged.

**The need.** 1.6.0's "Send to" dropdown offered only all owners or active licences.
The renewal campaign wants to email lapsed customers with age-appropriate copy (a
recent expiry gets the 30%/20% renewal discount pitch), which means targeting the
expired base in bands, not as one blob.

**How a band is decided.** `is_in_expiry_band()` first rules the owner out if
`has_active_licence()` says yes — active and lifetime licences never enter an expired
band. Then `licence_expired_at()` derives the expiry moment, in priority order:

1. `renewal_date` meta, end of that day UTC — authoritative when present;
2. `last_purchased_at` + 365 days (`ACTIVE_LICENCE_DAYS`) — the same fallback the
   active gate uses, so an ownership sits in exactly one of active/expired at any
   moment;
3. `days_since_last` minus 365, when only the day-count is known.

Bands are calendar-month boundaries via `strtotime('-6 months')` /
`strtotime('-12 months')` and are mutually exclusive: `expired_within_6_months` is
expiry >= six months ago, `expired_6_to_12_months` is < six and >= twelve,
`expired_over_12_months` is < twelve. An unknown stored scope value (e.g. after a
rollback to a build that predates the bands) falls back to "send to all", the
plugin's original behaviour, which keeps deploy order safe.

Covered by super-speedy-emails `.tests/37-support-type-admin-fields.php`, which
drives the real `should_send_to_user` gate through each band with reflection.

### Per-record version baselines

> * Each changelog Support Email now keeps its own "last emailed version" baseline,
>   so two records for the same product advance independently and one record's send
>   no longer uses up the release for another. Existing baselines carry over
>   automatically.

**The bug this prevents.** The "last version we emailed about" baseline was one
option per plugin slug (`sse_support_last_sent_version_{slug}`), shared by every
changelog record. With two records for the same product — the active-licence email
and the expired-within-6-months email — whichever fan-out completed first advanced
the shared baseline, and the second record's `should_send` then saw no news and
emailed nobody. Single-record installs never noticed; it bites the moment a second
audience exists, which is exactly what 1.6.2's bands create.

**The migration design.** Baselines are now stored per record as
`sse_support_last_sent_version_{slug}_{support_email_id}`. Reads fall back to the
old shared option when the per-record one is empty, so every existing and new record
inherits the live baseline once instead of re-baselining (which would email nobody
on the next release) or replaying history. The fallback read is deliberately
read-only during `should_send`; the shared option only advances inside
`maybe_advance_legacy_baseline()`, and only once EVERY changelog record targeting
that product has recorded the current version. That ordering means: the old
baseline survives while a second audience still needs it, and a record created
later inherits a completed baseline rather than the entire historical gap.

Covered by super-speedy-emails `.tests/52-changelog-independent-baselines.php`,
which drives `should_send`/`on_complete` for two records in the same sequence as
`SSE_Support_Emails::daily_check()`.
